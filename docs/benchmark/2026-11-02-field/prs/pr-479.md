What batch 2's summary says, verbatim: "Part 2 covers the mover, small changes to the switch
transaction and workspace view, and two tests. I found one bug to fix and one suggestion:"
followed by F5 ("when healing rolls a move forward, it deletes the source workspace's whole
`.kaipu/drag/` folder instead of just this item's drag folders") and F6, and ending "The
`switch-transaction.ts` and `workspace-view.ts` changes and both tests look correct."

So Wachiman read exactly this block: F5 is anchored on line 674, directly above the unguarded
`unlink` (675) and `removeCompanions` (676) lines. It did not approve those two lines in words,
but it approved "both tests", and the tests had no case where the source changed or was reused
while an entry waited. It had the answer on the next two lines and moved on.

Hypothesis, one line each:
- **D1:** needs reasoning across time (crash, then an unplugged target, then the user keeps
  working in the source, then healing returns); the diff shows only a cleanup that looks
  intended ("roll forward deletes the source"). Wachiman checked what the cleanup deletes
  (`drag/`) but not whether the source was still the thing it should delete.
- **D2:** an ordering bug in a cleanup path: a swallowed `.catch(() => {})` on `unlink`
  followed by an unconditional `done()`. A reviewer that treats `.catch(() => {})` on the
  happy path of recovery code as best effort will not see it.
- Contributing: the mover, the file that deletes user media, got a risk score of 5, below the
  group-move entry point (8), and 4 turns for 853 lines. The risk ordering under-ranked the
  most destructive file.
- On re-review (`670b1ba`) Wachiman summarised the fix ("deletes the source only while the
  source is still the item that was moved...") and marked the F5 thread addressed, so it
  understood the logic once the fix existed; it did not look for what the fix still omits
  (see "Bugs no bot found", item 3).

## Bugs no bot found

Defects the authors fixed or recorded that no bot raised in this PR.

1. **Same-volume hard-link move is unsafe inside Google Drive, OneDrive and iCloud folders**
   (a hard link renames or unsyncs the cloud item). Found by the fixing agent while working on
   #483, with no reviewer. Source: README (#483 section) and commit `c36db614`
   ("nothing is hard-linked into or out of a synced workspace ... a move with a synced side
   copies, verifies sha256 at the final path and then deletes"), which edits `move-item.ts`.
   Fixed after this PR. Severity: High for synced users (silent cloud damage).
2. **A running group move did not lock Change folder… (relocate).** Found at merge time and
   fixed in `413ee15` ("a running group move now also locks Change folder… (new 'moving'
   refusal, en and es), and activeTransactionDeps uses busyNow so relocate sees the move
   lock"). Wachiman's v1.4.0 review of that very merge approved it ("none that blocks the
   merge"). Source: commit message. Severity: Medium (a folder pointer changing under a
   running move).
3. **A title, tag or other record edit made in the source while a committed move waits is
   deleted by roll-forward.** The fix for D1 compares only the media (size, mtime) and the
   `.edit.json` byte for byte (`editProjectChanged`, `move-item.ts:748`); then
   `removeCompanions` deletes the sidecar. Stated by the fixing agent ("a title or tag change
   made in the source while the entry waited is not compared; I left that for a follow-up")
   in the F12 thread and the issue comment; still unchanged on `origin/main`. No bot raised it,
   including the Pullfrog/CodeRabbit proposals and the incremental re-reviews that approved the
   fix. Severity: Medium, unfixed.
4. **Quarantined moves have no user-visible surface.** The ADR commit `0ab3bd59` lists "a
   screen for quarantined moves" among what part 2 does not cover; healing only calls
   `console.error` (`index.ts` `healPendingMoves`), and `origin/main` renderer has no
   quarantine UI. Known gap, not a bug the authors fixed. Severity: Low-Medium. Source: ADR
   commit message; grep of renderer.
5. **Auditor observation (mine, reading only, not from the thread).** In the live path, if
   `rm(media)` throws after the commit, `healEntry` now returns "waiting" (unlink fails) and
   the catch ignores that result, returning `ok: true` while the source still holds the item.
   The user sees "Moved", the item exists in both workspaces with the same assetId until the
   next heal. Pullfrog listed the live path in its details block ("still returns ok: true,
   whatever the heal did") but not this consequence; the fix kept `ok: true`. Low; unverified
   by a run.
