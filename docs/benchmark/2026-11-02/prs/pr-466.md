### Evidence

- **NF1.**
  - `openInMain` is `showMainWindow(); sendToRenderer(recordingReadyOpen, handOff)` with no active-take check (index.ts:899-902). The deep-link path guards with `if (!hub?.isActive()) showMainWindow()` (index.ts:185). `triggerStartRecording` refuses with the comment "Don't un-hide the (deliberately hidden) main window into an active recording — it would get burned into the video" (index.ts:475-478). The hub hides the main window at take start (recording-hub.ts:689).
  - **Is the card still up during the next take?** Yes in code. The window has no timer and hides only on action, X or Escape (recording-ready-window.ts:88-90, 149-155, 166-172). `recordingReady` is referenced only at index.ts:664, 897 and 1093 (shutdown), so nothing in the hub closes it at take start. The card also survives that take by design (content protection at :206-208). So pressing a chip during the next take reaches `showMainWindow()`.
  - **Answer to the specific claim.** The press does show the main window during recording. The main window is not content-protected in the code I read, and the repo's own comment says an un-hidden main window gets burned into the video.
  - **Unconfirmed:** that navigating to Prepare or the editor kills the recorder. The recorder runs in the main renderer (comment at index.ts:459-462), but I did not find whether it lives above the router.
  - Not fixed on origin/main: openInMain at index.ts:987-990 is still `showMainWindow(); sendToRenderer(...)` and `git log b2705a9..origin/main` on recording-ready-window.ts shows only 1ff66f1b.
- **NF2.** `fullDisplayBorderAllowed` documents that content protection paints the window black before Windows 10 build 19041 (area-geometry.ts:81-92), and the hub uses it to skip the display border (recording-hub.ts:701-703). The capture toast is dismissed by `dismissToast` in `beforeCapture` (capture-window-hooks.ts:52-56, index.ts:670) and treats content protection as a "second guard" (capture-toast-window.ts:305-307). The ready card has only the first guard (recording-ready-window.ts:206-208). No gate on the platform build in `show()`. Not run; whether that Windows range is still supported by the app's Electron version is unchecked.
- **NF3.** `doDelete` calls `remove(localId)` then `back()` (library-detail-page.tsx:212-217). `useFloatingReadyCard` has no unmount cleanup (use-floating-ready-card.ts:21-29) and the window has no tie to the page. The hand-off then navigates to a route for a deleted id. Worst case is a "File not found" page, so Low. No close channel exists on origin/main (grep for a close/hide bridge found none).
- **NF4.** Base gated nothing on the probe (`showCard` only, base library-detail-page.tsx:128-134, 242); head gates on `probeSettled` (:140-142, :155), so the gating is real. But `probeSource` catches every throw and returns null (probe-source.ts:42-43), which becomes "error" and settles. A promise that never resolves is hypothetical and not shown anywhere. Reviewer itself said low confidence.
- **NF5.** Doc line floating-ready-window.md:51: "the card never shows twice". Read in context it means not both in-app and floating, which holds; read literally it contradicts E3. Wording issue only.
- **NF6.** The two new tests (library-detail-page.test.tsx:741-766) assert one ask per mount and the fallback; the only `router.navigate` in the file is at :248 in another test. Origin/main's later fix moved to module-level `askedKeys` with a test reset hook, which implies the gap was real.
