# ADR 0054: The loop records each round and renders a review summary comment from code

- **Status:** accepted 2026-11-14 by the owner. Implemented by the pull request that adds this
  file (`loop-review-summary-publish`). Amends
  [ADR 0034](0034-a-review-loop-driven-by-the-cli-that-never-edits-code.md): its state file gains
  per-round data and the loop gains an output, the summary comment. Reuses the repository settings
  file of [ADR 0048](0048-a-repository-settings-file-at-the-root-wachiman-yml.md) and the
  base-commit rule of [ADR 0049](0049-model-and-effort-in-wachiman-yml-read-from-the-base-commit.md).
- **Date:** 2026-11-14
- **Numbering:** 0054 is the next number above every ADR on `main` and in an open pull request on
  this date.

## Context

A loop ends with a number of things a reviewer of the pull request wants to know: how many rounds
ran against the budget, which Wachiman version and models did the reviewing, what the review cost,
what range it read, what was fixed, what was declined and what still needs a person. ADR 0034's state
keeps only the base, the head of each round and the findings, so none of that could be told from code.
An agent that wanted to put it on the pull request wrote the table by hand, and by hand it went wrong:
a loop run that way used its own fix commits as round bases, which left those fixes unreviewed, and
the round ranges and counts in the table were the agent's reading of the history, not a record.

## Decision

1. **Each round records what its review reported about itself,** copied from the review result and
   never estimated: the base sha it actually read (the merge-base of the round's `from` and its
   head), the Wachiman version, the reviewer model and effort, the verifier model and effort (absent
   when verification was off), the API-equivalent cost and the duration of the run (the verifier call
   included), the number of findings reported and how many were new to the loop. A finding records the
   round that first reported it. The state also records the round cap of the last call.
2. **The state format is `wachiman.loop-state/2`.** A `/1` state still reads: its rounds have no review
   data and every summary row built from them says `not recorded`; the next round writes the state
   back as `/2`, keeping the old rounds. A result that lacks a figure (cost, time, version, model)
   records no review data for that round rather than a zero. A round with no new commit makes no review
   call and records none. The dashboard's index reads both formats.
3. **A later round's base is the previous round's head,** which the loop already did. A test now pins
   that consecutive recorded ranges meet.
4. **The summary comment is generated by code from the state and the verdicts.** One module renders a
   Markdown document: a table (review kind and who posted it, reviewer versions, models, rounds against
   the budget, findings by outcome, range reviewed, cost and time), a **Needs your judgment** list (only
   findings a person must decide: still open, judged wrong with a reason, or judged partly right), and a
   collapsed list of every round and every finding with its plain-word status. When versions or models
   differ across rounds the rows say which rounds ran under which. Rounds with no data are named and
   never counted as zero. Text a model or a person wrote is made safe for a table cell (no tags, no
   comment, no mention, no pipe). The output is pinned by golden files and passes markdownlint's default
   rules, with one invisible directive that turns off the three rules a table, a collapsed block and a
   footnote cannot meet (line length, inline HTML, first-line heading).
5. **The first line is a marker that carries the kind of summary:** `<!-- wachiman-review-summary:local -->`.
   The kind is written in one place in the code, so a `remote` summary of a pull request review can
   exist later under the same scheme without a second mechanism. A comment is recognised by starting
   with the marker and by being the signed-in account's own.
6. **The loop prints the summary and publishes it only when asked.** `wachiman loop --format markdown`
   prints it after a round; `--summary` prints it for the open loop with no round, no model call and no
   write. `--publish` finds the open pull request whose head is the current branch with `gh` and creates
   the comment, or edits in place the comment with the marker that the signed-in account posted.
   `--no-publish` turns a configured publish off for one call. `publishLoopSummary: true` in
   `.wachiman.yml` makes every call publish; it is read at the merge-base of the loop's `--base`, never
   from the branch under review, for the reason ADR 0049 gives. A failed publish is said on stderr and
   never changes a round's exit code. `--agent <name>` (or `WACHIMAN_AGENT`) says an agent posts it.
7. **The shipped `wachiman-loop` skill drives it.** The agent runs the loop before opening the pull
   request, publishes the summary right after the pull request opens so it is the first comment, and
   publishes again after each later round, which edits it in place. It never writes the table.

## Alternatives rejected

- **The agent writes the table by hand.** It is what went wrong: round ranges and counts came from the
  agent's reading of the history, a hand-run loop used fix commits as bases, and the figures could not
  be checked against anything. Code that owns the state is the only source that cannot miscount it.
- **Publishing by default.** The comment is posted under the developer's own GitHub account, which must
  be their choice for a call or, through a committed setting, for a repository. A default would post
  from every laptop that runs the loop.
- **A separate configuration file for the publish opt-in.** `.wachiman.yml` already exists for repository
  settings and ADR 0048 says there is one file in one place.
- **Reading the opt-in from the working tree.** A branch could then switch publishing on for whoever
  runs the loop on it; the base-commit rule of ADR 0049 exists so a change cannot choose what it runs under.
- **A section of the round JSON or the terminal report instead of a separate output.** Those are for the
  agent that fixes between calls; the summary is for the people who read the pull request.

## Consequences

- A loop state written by this version is not readable by an older Wachiman (its `/1` reader refuses
  `/2`); an older state is read and upgraded. The error tells the older reader to start a new loop.
- The summary's figures are API-equivalent estimates reported by the run, not a bill, and say so.
- The `gh` call acts as whichever account `gh` is signed in with. Wachiman does not choose or check it;
  a developer with several accounts selects the right one before publishing.
- Findings the verifier dropped and findings judged wrong appear in the summary as declined, with the
  reason of a judgment, so a person can overrule them.
- `publishLoopSummary` is one more key that nothing but `wachiman loop` reads.

## Non-goals

- A `remote` summary of a pull request review on GitHub. The marker has room for it; nothing renders it.
- Publishing from CI, or to anything but the open pull request of the current branch.
- Editing a comment the signed-in account did not write, or finding a comment by anything but the marker.
- Choosing the GitHub account: that stays the developer's setup.
- A guard against posting from a company-account repository. The repository has none for any command
  today; adding one is a separate decision.

## Reopen when

- A `remote` summary is built: decide whether it shares the table and what a pull request shows when
  both exist.
- A second place needs the per-round data (the dashboard, a status line): decide whether the state or
  the history store owns it.
- Posting under the developer's account turns out to surprise people even behind `publishLoopSummary`:
  decide whether the opt-in moves from the repository to the person.
