# Engine benchmark baseline, 2026-11-21

The first committed baseline of how long the engine takes, without model time and without network.
This is an engine timing report, not a review-quality report (those live in the benchmarks repository),
so it stays here beside the script.
It is the starting point for moving hot paths to Bun-native APIs: nothing is changed until a number
here shows it is hot. Each later change reports before and after numbers from the same script.

## How to run

```sh
bun install --frozen-lockfile
bun run bench                # a table: median, min, p90, runs
bun run bench --json         # the same numbers, plus date, commit, Bun, Node and CPU model
bun run bench --runs 25      # more runs for the CLI and review cases (default 15)
```

The script is [`scripts/bench.ts`](../../scripts/bench.ts). Every run must exit 0: one nonzero exit
fails the bench with exit 1. It is POSIX only (macOS, Linux).

- Commands run with the repository's own pinned Bun (`node_modules/.bin/bun`), called by path. The
  bench does not put `node_modules/.bin` on `PATH`.
- `HOME` and `WACHIMAN_HOME` point to a temporary directory, so no local profile or history leaks in.
- CLI and review cases run 2 warm-ups and 15 timed runs. The test case runs 1 warm-up and 5 timed runs.
- It records the Bun version, the Node version and the CPU model. It never records a host name.

## What each case measures

| Case | What it times |
| --- | --- |
| `launcher --version (under bun)` | `bun bin/wachiman.js --version`: the launcher's Bun probe plus the child Bun that starts the CLI |
| `launcher --version (under node)` | `node bin/wachiman.js --version`: the same, with Node hosting the launcher (the npm path) |
| `launcher --help (under bun)` | the same path, printing the help |
| `launcher local --help (under bun)` | the same path, printing the `local` help |
| `tests: engine fakes` | `bun test src/engine.fake.test.ts src/full-review.fake.test.ts`: the engine against a fake provider |
| `local review (fake claude, e2e)` | `wachiman local --repo-dir <fixture> --base main` end to end: git reads, review input, the fake `claude`, parsing and printing the result |

The review case runs on a fixed fixture, the repository `branchRepo()` builds in
`test/support/temp-repo.ts` (five files changed between `main` and `feat/x`: an edit, an add, a
rename, a binary change and a rules file). The fake `claude` is a small shell script on `PATH` that
answers the version probe and the sign-in check, reads the prompt and prints one fixed review. It
makes no model call and no network call. Its response is a copy of the one in
`test/local-fake-provider.test.ts`, which compiles a Bun executable instead; a Bun 1.3.4 compiled
executable is killed on some macOS versions, and a script keeps a large process start out of the timings.

Because every launcher case runs `bin/wachiman.js`, these numbers are not `bun src/cli.ts` alone.

## Reference machine

An Apple M4 is the reference class. The table below was measured on an M4 desktop (Mac mini); an M4
laptop was not reachable that day. Do not compare it with an M5 or a loaded machine.

| | |
| --- | --- |
| CPU | Apple M4 |
| OS | macOS, darwin-arm64 |
| Bun | 1.3.4 (the repository's pinned version) |
| Node | v24.21.0 |
| Commit | `72cffec`, the final script; the engine is `main`'s, unchanged |
| Load | load average about 1.9 before the run |

## Result

`bun run bench`, exit code 0:

| Case | Median | Min | p90 | Runs |
| --- | --- | --- | --- | --- |
| `launcher --version (under bun)` | 56.9 ms | 54.0 ms | 61.2 ms | 15 |
| `launcher --version (under node)` | 67.7 ms | 64.8 ms | 71.7 ms | 15 |
| `launcher --help (under bun)` | 57.5 ms | 54.7 ms | 60.1 ms | 15 |
| `launcher local --help (under bun)` | 57.1 ms | 50.2 ms | 60.0 ms | 15 |
| `tests: engine fakes` | 383.8 ms | 374.7 ms | 396.2 ms | 5 |
| `local review (fake claude, e2e)` | 475.2 ms | 394.1 ms | 483.2 ms | 15 |

With 5 runs, the p90 column is the slowest run. Spread in this run: the CLI cases have a p90 within
8% of their median and the fake tests within 4%. The review case has a p90 within 2% of its median
but a minimum 17% below it, so it is the noisiest. Two earlier runs of the same script (before its last small edits) gave review medians of
475 ms and 518 ms and p90 values of 590 ms and 618 ms, so a change under roughly 20% on the review
case is noise until more runs say otherwise. Three runs are too few to set a firm floor.

## Earlier numbers, for context

Measured on commit `f6bd3af` with a throwaway version of the script and the same pinned Bun, median
of 15 runs after 2 warm-ups (5 runs for the fake tests). That script put `node_modules/.bin` on
`PATH` and set `WACHIMAN_HOME`, and it had no review case.

| Metric | M4 Pro laptop | M4 Mac mini |
| --- | --- | --- |
| `--version` via Bun | 50 ms | 56 ms |
| `--version` via the Node launcher | 60 ms | 74 ms |
| `--help` / `local --help` | 50 / 51 ms | 50 / 50 ms |
| engine fake tests | 0.36 s | 0.38 s |

The new Mac mini numbers are within about 10 ms of these (the Node launcher case is 6 ms faster, 68 ms against 74 ms). The full test suite, run
serially, took 284 s on the M4 Pro laptop and 339 s on the Mac mini; the bench leaves it out on purpose.

## Comparison on every PR and history of `main`

`.github/workflows/bench.yml` runs the bench on the base and on the head of each pull request, on the
same runner, five interleaved rounds each, and posts one comment (updated on every push, found by a hidden
marker) with each case's base median, head median and change in percent. The job fails when a case is more
than 15% and at least 10 ms slower. Pull requests from forks and from Dependabot get the table in the job summary only.
On ubuntu-latest, with base and head the same commit, the median of five rounds differed by at most 3.4%
(18 results over 3 runs); one round alone differed by up to 14.2%, which is why the rounds are interleaved
and medians are compared. Absolute times moved by 2.5x between runs, so only the in-run change means anything.

Every push to `main` appends one line to `bench-history.jsonl` on the `bench-history` branch, and keeps the
JSON of every round as a workflow artifact. Each line is a controlled measurement: the job measures the pushed
commit and its first parent on the same runner, interleaved, the way a pull request compares base and head. A line
holds, per case, the parent median, the commit median and the change in percent, plus the runner identity (OS,
architecture, CPU model) and the Bun version. Absolute medians are only comparable within one line, because runners
differ by up to 2.5x; the trend to read is the change per commit. History jobs run one at a time; a merge that
lands while two others wait can be skipped, which leaves a gap and nothing else. A table of the trend:

```sh
git fetch origin bench-history && git show origin/bench-history:bench-history.jsonl > /tmp/history.jsonl
bun scripts/bench-history.ts /tmp/history.jsonl --last 30
```
